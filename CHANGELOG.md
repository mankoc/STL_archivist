# Changelog

## Unreleased

- **Web client step 6b: editing.** Editors can edit table cells in place (double-click), open the model editor with completion lists, drop images onto a model, remove images, and remove selected models from the library (Ctrl/Shift-click to select several). Viewers see no editing controls.

- **Rust migration, Phase 6 begins: the web client (step 6a).** `web/` holds the new browser front end (React, TypeScript, Mantine), served by the server. You can sign in, set up the first administrator, and browse the library: the filter pane with include/exclude values, has-value groups and counts, search, a fast virtualised table with server-side sorting, and a detail pane with thumbnails and the archive download. Its API types are generated from the server's OpenAPI description.

- **Server step 5e, completing Phase 5: server files and Docker.** Editors choose folders to crawl by browsing the server's disks, limited to the library's folders unless they are administrators. Anyone signed in can download an archive. Remote clients get a folder path to open only where `server.json` maps the server's paths to theirs. `stl-server create-admin` sets up the first administrator on headless machines and in containers. A `Dockerfile` builds the server with PDF and AI-embedding support included (not yet test-built).

- **Server step 5d-2: PDF previews and AI embeddings without Python.** When it finds pdfium and ONNX Runtime, the server renders PDF previews and computes CLIP embeddings itself, during crawls and as a *compute embeddings* job. Its vectors match the desktop app's (cosine above 0.9999), so both can share one library. The image preparation for CLIP is native and checked against the Python version.

- **Server step 5d-1: jobs and live events.** The server runs crawls and maintenance (verify archives, recompute image hashes, prune images, compact the database) as jobs, one at a time, which can be cancelled. Progress, log lines and library changes stream to clients over a WebSocket (`/api/events`). A server crawl catalogues a folder exactly as the desktop app does. The exceptions are PDF previews, AI embeddings and AVIF or CMYK JPEG images, which the server cannot produce yet.

- **Server step 5c: editing.** Editors can now change the library through the server: browser cell edits, the model editor, the mass editor (path patterns, templates, find & replace), removing models, adding and removing images, and the tag, category, collection, subcollection, scale and creator editors. As in the desktop app, edits refresh the folder's `METADATA.7z` in the background (when sidecars are enabled), and a sidecar written by the server restores in the desktop app.

- **Server step 5b: user accounts.** The server now requires signing in. Users have one of three roles: viewer (read only), editor or admin (also manages users), and each user can store their own settings. The first administrator is created on the server's own machine (`POST /api/auth/setup`); after that, admins create the other accounts. Passwords are stored as Argon2 hashes, sessions end after 30 days without use, and five failed sign-ins lock a name out for 15 minutes. Accounts are kept in `server.db` in the data directory, separate from the library database.

- **Rust migration, Phase 5 begins: the stlLibrary server (step 5a).** `rust/stl-server` serves a library read-only over HTTP: the browser table's ids and rows with filters, search and sorting, the filter pane's values and counts, model details and thumbnails (cacheable forever, because the store is content-addressed), with an OpenAPI description. Run it with `cargo run --release -p stl-server -- --data-dir <dir>`. There is no authentication yet, so it listens on `127.0.0.1` only.
- **A library is open in one process at a time.** The desktop app now refuses to open a library that another app instance or the server has open, and says which process holds it. The lock is released when that process ends, even after a crash.

- **Rust migration, step 4h: the native core is now required, and SQLAlchemy is gone.** Every database read and write, on every platform, goes through the Rust core, which also owns the schema. The `STL_NATIVE` switch is removed. Python remains only for what the core hands back: archives it cannot read exactly, images only Pillow decodes, PDF pages and CLIP embeddings.
  - Dependencies dropped: SQLAlchemy, lmdb and the sqlite-vec Python package. sqlite-vec is built into the native core.
  - Mass Editor → Find & Replace in regex mode now runs natively. It uses the Rust `fancy-regex` dialect, which is Unicode-aware and supports lookarounds and backreferences, with Python's replacement rules (`\1`, `\g<name>`, `\n`). A pattern it cannot read is reported and nothing is saved. A tag listed twice is linked once instead of failing.
  - Dates and sequence numbers written with non-ASCII digits (for example Arabic-Indic) are parsed natively.
  - Configuration → Debug: the *Log SQL statement timings* option is removed, because it timed SQLAlchemy statements.
  - Tests: every test gets its own database file, and test data is built with plain `sqlite3` (`tests/factory.py`).

- **Rust migration, step 4g-5b: the crawl itself runs natively** (on Windows): listing, hashing, extraction and thumbnails in parallel, saving, sidecars, and move and deletion handling. Results are identical to the Python crawler (golden-tested, and on real library folders); PDF previews, CLIP embeddings and the few image formats only Pillow reads are still produced by the Python code during a native crawl.
- **Fix:** crawling a folder without subfolders no longer treats its own `METADATA.7z` sidecar as an archive.

- **Rust migration, step 4g-5a: RAR archives are listed and read natively.** Archive contents and fingerprints come from a port of the `rarfile` reader (verified against every RAR archive of a 60,000-archive library), and data is read through the UnRAR tool as before. Listing a RAR archive is now near-instant.

- **Rust migration, step 4g-6: Generate Thumbnails, Rescan, Recrawl and Update Crawled Folders save natively** (on Windows), with results identical to the Python code.
- **Fix:** *Recrawl* now uses the configured UnRAR tool and crawler settings, so `.rar` archives no longer fail to re-extract.

- **Rust migration, step 4g-4: the crawler's database work runs natively** (on Windows): change detection, move matching, saving new and changed archives, and the clean-up of missing records. Results are identical to the Python code (golden-tested over a multi-step crawl, and on real library folders).
- **Fix:** a folder path pattern no longer overwrites a release, sculptor or collection that the same crawl has just taken from `info.json` or from the crawl's forced values. Before, that depended on internal timing.

- **Rust migration, step 4g-3: METADATA.7z sidecars are written and read natively** (on Windows). Writing is about 9 times faster, because thumbnails are stored instead of being recompressed. Records restored from a sidecar now get their folder set, so folder views show them at once.

- **Fix: the thumbnail store no longer grows by 2 GB every time it is opened.** On Windows the store's `data.mdb` takes the size of its memory map, and the map was sized from that file plus 2 GB of headroom, so each start of the application (and each test run) enlarged it. The map is now sized from the space actually in use. The space is allocated sparsely, so disk usage did not grow with it. An enlarged file keeps its size until *Database Maintenance → Compact Thumbnail Store* rewrites it.

- **Rust migration, step 4g-2: model metadata is inferred natively** (title, creator, source, release date and URL from the path, `.url` files and `info.json`). Results are identical to the Python code on a 60,000-archive library.

- **Presupport patterns are checked when saved.** Configuration now refuses a custom pattern that uses syntax the crawler's native engine would read differently from Python (for example `\w`, named groups, inline flags, POSIX classes or non-ASCII characters) and explains why. Patterns that pass the check run in the native rules, which are faster. See *Help → Configuration → Warnings* for the accepted syntax.

- **Rust migration, step 4f-4d: the crawler tab's folder list and the browser's cell edits run through native-backed services** (on Windows). Every dialog except the crawler-driven ones (rescan, thumbnail generation, re-crawl, Update Crawled Folders) now works without the Python database layer.

- **Rust migration, step 4f-4c: Database Maintenance reads and writes natively** (on Windows). This covers embeddings, the warning re-check, Find Moved, merging moved records, removing records and the free-space figure for Compact.
- **Fix:** *Remove from database* in Database Maintenance now also deletes the removed records' thumbnails, and relocating a missing archive updates its folder as well as its path.

- **Rust migration, step 4f-4b: Find Duplicate Archives (content) and the folder lists run natively** (on Windows). The STL file-list comparison now takes 1.3 s instead of 2.9 s on a 60,000-model library, and pairs with equal similarity are listed in a consistent order. The image comparison's reads, the crawled-folder list and the sidecar dialogs' folder list also run natively.

- **Rust migration, step 4f-4a: the viewer dialogs read natively** (on Windows). This covers Archive Contents and its compare view, Image Browsing, the image grid, Find Duplicate Archives and Find by Image. Results are identical to the Python code (golden-tested). On a 60,000-model library, Find Duplicate Archives loads its data 38 times faster.

- **Rust migration, step 4f-3: the browser panel, statistics and the sort dialog read and write natively** (on Windows). This covers the info panel, thumbnails, dropped images, Delete from DB, Add Tag, the edit-cell lookup lists, Statistics, Column Distribution and Sort Files. Results are identical to the Python code (golden-tested). Statistics rankings now order models with equal counts consistently.
- **Fix:** sorting files into a directory now updates the archive's folder as well as its path, so folder views show moved archives in their new folder at once.

- **Rust migration, step 4f-2: the model editors save natively** (on Windows): the Edit Model dialog, the AI tagger and the Mass Editor, including path-pattern parsing, `{token}` templates, Find & Replace and trimming. Results are identical to the Python code (golden-tested over random edits). A regular-expression Find & Replace still runs in Python, because the two regex engines differ in details.

- **Rust migration, step 4f begins: the lookup editors run natively** (on Windows). Tag, Category, Collection, Subcollection, Scale, Author and creator profile editing all go through a shared service, with identical results (golden-tested over random edit sequences). Renaming an author to an existing name no longer holds the database locked while asking whether to merge.

- **Rust migration, step 4e: maintenance and image search run natively** (on Windows): *Verify Archives* (files are checked in parallel; about 1.8x faster when the drive's metadata is cached), *Find Duplicate Entries*, *Prune Images*, reading the stored AI embeddings, *Find by Image* by embedding, and the embedding duplicate search. Results are identical to the Python code on the reference library. *Verify Archives* and *Find Duplicate Entries* now always list records in the order they were added.

- **Rust migration, step 4d: edits made in the browser table are saved natively** (on Windows), with the same rules as before: tags are lowercased and de-duplicated, a subcollection belongs to its collection, and the modification time only changes when a field really changes. Removing unused lookup values also runs natively. Moving and deleting records are ported too, and switch over with the crawler and dialogs later. Edits containing non-Latin digits (a date such as ٢٠٢٤) are saved by the Python code, as before.

- **Rust migration, step 4c: the browser's queries run natively.** On Windows, the main table's row ids and rows, the filter pane's values and counts, and the lookup editors' usage counts come from the native core. On the reference library they returned identical results to the Python queries. Loading rows is 4x faster and rebuilding a filtered filter pane is 2.9x faster (27 filter combinations: 5.4 s instead of 15.5 s). Other platforms keep the Python queries until the move away from SQLAlchemy is complete, because two SQLite libraries in one process can corrupt a database there.

- **Browser table order is now reproducible.** Rows that tie on the sort column (same title, same creator) are ordered by when they were added, instead of by whatever order SQLite's query plan happened to give. A model's tags and scales are always listed in the order they were created. Internally, the browser's queries moved into Qt-free services (`library_query.table_ids` / `page_rows` and the new `services/filter_tree.py`), ready for the native core.

- **Rust migration, step 4b: the native core migrates the database schema.** At startup, `stlLibrary.db` is brought up to date by Rust: old table and column renames, the dhash column fix, new tables, columns and indexes, the vector table and the view. The SQL is generated from the SQLAlchemy models (`tools/gen_schema.py`), so a database comes out byte-identical whichever side migrated it. That was checked on five generated legacy databases and on a copy of the reference library. The Python migration remains the fallback.

- **Rust migration, Phase 4 begins: crawler rules, path patterns and Soundex run natively.** The presupport classification, archive warnings, scale detection, folder path patterns and Soundex now go through the native core, with the Python versions as the fallback. On the reference library they gave identical results for 484,744 path parses, the member lists of 2,998 archives and 53,841 names. Path parsing is 2.5x faster.
  - A custom list of presupport filename patterns (Configuration → Crawler warnings) is always applied by Python. The two regex engines read some syntax differently without reporting an error, so a native run could flag different archives. The built-in patterns run natively.
  - Plan: Phase 4 now runs in steps 4a–4h, and the open decisions are settled. The PyQt app becomes a shell over the Rust core; the server gets user accounts; the web client uses Mantine; and the PyQt app is removed as soon as the web client reaches parity (`docs/rust-migration-plan.md`).
  - Tests: a test that switched the native core off could leave it on for the following tests, so part of an `STL_NATIVE=0` run quietly used Rust. A shared fixture now resets it after every test.

- **Rust migration, Phase 3: the thumbnail store runs on the native core.** With the native core installed, `thumbnails.lmdb` is opened through Rust (heed) instead of py-lmdb. The on-disk format is unchanged and byte-identical: same keys, same shared blobs for identical thumbnails, same collision handling. A library still opens with either build, and switching back and forth is safe. Without the native core, py-lmdb is used as before.
  - All store access goes through one backend chosen when the store opens. LMDB forbids opening the same store twice in one process, so the two implementations never touch it together.
  - Opening the store no longer writes to it.
  - New golden tests write with one implementation, read with the other, and compare the raw keys. On the reference library, 30,000 random thumbnails and the store statistics read identically through both.

- **Rust migration, Phase 2b–2c: native thumbnails and a new perceptual-hash format.**
  - **Thumbnails are made by the native core** for JPEG, PNG, WebP, BMP, TIFF and GIF, animated GIFs included. On 1,022 images from the reference library this was 1.7x faster than Pillow: PNG 2.2x, JPEG 1.4x. JPEGs are decoded at a reduced DCT scale when that still leaves at least twice the target size. Output sizes are exactly Pillow's `Image.thumbnail` sizes. Pixels differ from Pillow's by 1.2/255 on average (at most 4.9), and the files are the same size. AVIF, CMYK JPEGs and anything the native core cannot decode still go through Pillow.
  - **Fixed: 16-bit greyscale PNGs no longer come out almost white.** Pillow converted them to RGB by clipping at 255; they are now scaled to 8 bits.
  - **Perceptual hashes (dHash) have a new format, computed only by the native core.** The method is the same: 8-bit luma, Lanczos down to 9×9, horizontal and vertical gradients, 128 bits. But Rust's decoders and resampler are not Pillow's, so the bits differ, and one library must not mix the two. New hashes are stored as `2:` plus 32 hex digits, and older ones count as missing. On 2,000 reference thumbnails the new hash is at least as robust as the old one (re-encoding at JPEG quality 50: mean distance 1.1 vs 1.2 bits) and separates unrelated images equally well.
  - **Run _Database Maintenance → Recompute Image Hashes_ once after upgrading.** It now reads thumbnails in batches, hashes each batch in parallel natively and writes it in one statement. Hashing is about 30x faster than before, but on a hard disk the run still takes about an hour for 365,000 images because reading thumbnails dominates. Until then, searches compute missing hashes on the fly (without saving them).
  - **Without the native core no perceptual hash is computed.** Images without a current hash are left out of perceptual-hash searches, and _Find by Image_ offers the AI embedding method only. It used to refuse every image it could not hash, even for the embedding search.
  - The hash recompute moved from the maintenance dialog into `services.maintenance.recompute_dhashes`.
  - PDF first pages are still rendered by PyMuPDF; pdfium comes later.
  - New tests: `tests/golden/test_thumbnail_golden.py` (sizes, formats and pixels against Pillow, fallbacks), `tests/test_dhash_recompute.py`; the hash tests cover the new format and running without the native core.

- **Rust migration, Phase 2a: the crawler reads `.zip` and `.7z` archives natively.** The catalog (names, CRCs, sizes) behind `archive_hash`, and the extraction of images, `info.json` and `.url` files, now go through the native core when it is installed. RAR archives still use UnRAR.
  - **Hashing archives is much faster.** Reading the catalogs of 300 sample archives took 4.7 s in Python and under 0.1 s natively. These figures come from the file cache, since Python read the same files first. Extraction is about 1.3x faster; it is bound by decompression and disk.
  - **The results are the same.** The ZIP reader ports CPython's `zipfile`: CP437 and UTF-8 names, Unicode-path extra fields, NUL and backslash handling, ZIP64, data before the archive, and the per-member checks that make `zipfile` skip a member. Rust recomputed the hash of every `.zip` and `.7z` archive in the reference library (60,487). Wherever the stored hash differed, Rust's matched what Python computes today: 25 archives had changed since their crawl, and 73 had once failed to open in Python. For a random sample of 3,000 archives, the files Rust extracted (29 GB) were byte-for-byte identical to Python's.
  - **Anything unusual is left to the Python readers.** This covers encrypted members, compression methods other than stored and deflate, and archives Rust cannot parse. The fallback is per archive and silent.
  - Fixed before release: `sevenz-rust2`'s block decoder silently drops the last files of a solid block that has a directory or empty file inside it. py7zr writes archives laid out like that. Rust detects those blocks and leaves those archives to py7zr.
  - New golden tests (`tests/golden/test_archive_golden.py`) build ZIP files byte by byte to cover each naming edge case, and compare catalogs and extracted bytes with `zipfile` and py7zr.

- **Rust migration, Phase 1: faster duplicate searches.** Three all-pairs searches now run on the native core, with the Python code kept as the fallback. Timings are from the reference library.
  - **_Find Duplicate Archives → Images_ by perceptual hash: 15.7 s → 3.9 s.** The Hamming scan over 191k distinct hashes takes 2.1 s instead of 13.9 s in NumPy, with identical pairs.
  - **_Find Duplicate Archives → Images_ by AI embedding: 66 s → 36 s.** The scan uses `gemm`, which picks AVX2 or AVX-512 kernels at run time. The NumPy and Rust scans can disagree only on pairs within float rounding (about 1e-6) of the threshold; on the reference library that was 19 of 1.66 million pairs.
  - **_Find Metadata Duplicates_ by Levenshtein: minutes → seconds.** All 51k distinct titles at distance ≤ 2 take 3.3 s; the Python search took an estimated 21 minutes or more. Identical values are now compared once and expanded back to model pairs. The lookup editors' _Merge similar_ (collections, subcollections, categories and the rest) and the author editor use the same function.
  - Long native operations report progress and honour _Stop_. Each scan runs on a worker thread while the calling thread relays progress every 100 ms, so no Python callback runs on a Rust thread.
  - The native core is built for x86-64-v2, which includes hardware popcount; every x86-64 CPU since about 2009 supports it. `tools/build_native.py` now runs Cargo from `rust/` so that this setting applies.
  - New golden tests compare each Rust scan with its Python version, and the duplicate-finder tests run against both.
  - Plan change: perceptual-hash computation moves to Phase 2 with the image pipeline, and path patterns, crawler rules and Soundex move to Phase 4 with the crawler (see `docs/rust-migration-plan.md`).

- **Rust migration, Phase 0: an optional native core.** The codebase is moving to Rust step by step, towards a server that owns the library and a React web client in front of it, like Jellyfin (plan: `docs/rust-migration-plan.md`).
  - New Cargo workspace in `rust/`: `stl-core`, the core library, and `stl-py`, PyO3 bindings that install as the `stl_native` Python module. One `abi3` build covers Python 3.12 and later. Build it with `python tools/build_native.py`; `build_dist.py` builds it before PyInstaller and bundles it, or skips it with `--no-native`.
  - The module is optional. `app/native.py` loads it when present, every ported function keeps its Python fallback, and `STL_NATIVE=0` turns it off. The first log line says whether it is in use.
  - First ported function: the archive fingerprint behind `archive_hash` (xxh64 over member names and CRCs). New golden tests (`tests/golden/`) require the Rust and Python results to be identical. Rust also recomputed the stored hashes of every ZIP (51) and RAR (106) archive and 150 `.7z` archives in the reference library, all identical.
  - Decisions recorded in the plan: perceptual hashes and CLIP embeddings get new Rust implementations and are recomputed once; PDF thumbnails will use pdfium; RAR keeps the external UnRAR tool.
- **Documentation:** new `docs/rust-migration-plan.md`, covering the architecture, phases, crate choices, the compatibility rules for sharing one library between the Python and Rust code, and open decisions. `docs/server-migration-plan.md` is marked as superseded by it. `class_diagram.md` is regenerated from the source: package and module dependency graphs, data model, crawler, services, UI composition and hierarchy, a table of background workers, and the import cycles still present.

- **_Find Duplicate Archives → Images_ is much faster, and complete.** On a 363k-image library the perceptual-hash search takes 16 s and the AI-embedding search 66 s.
  - **Fixed: the perceptual-hash search could stop early and miss duplicates.** It ended the scan after five consecutive rounds of 50-image chunks found no new pairs, which on a large library could happen after the first thousand images. Every pair is now compared.
  - **The AI-embedding search no longer takes hours.** It compared vectors in `float16`, which NumPy cannot pass to its optimised matrix routines, with a Python loop per image. It now multiplies `float32` tiles in BLAS.
  - **Identical images are compared once.** About half the images in a typical library are byte-identical renders shipped with several releases; 363k images held 190k distinct ones, so the quadratic scan does a quarter of the work. Hashes are compared with a cache-tiled, multithreaded XOR + popcount (`np.bitwise_count` on NumPy 2).
  - **New: _Skip images shared by more than N archives_** (default 10), for both methods. Studios ship the same banner or promo render with every release; in the reference library seven such images each appear in 749 archives, which produced millions of meaningless pairs. An image is skipped when it, or a near-identical copy, appears in more than N archives, and the status line reports how many were skipped.
  - **The results table no longer freezes the window.** Archive sizes come from the database instead of a `stat()` per row on the GUI thread, the table is sized once instead of growing row by row, and hover thumbnails load on first hover instead of all up front. At most the best 100,000 pairs are listed.
  - After _Stop_, the status now says _Search stopped._ instead of _No similar image pairs found_.
  - The search logic moved out of the dialog into `app/services/image_duplicates.py`.
- **Fixed: perceptual hashes made only of digits were destroyed.** In databases from early versions, `images.dhash` was declared `INTEGER`, so SQLite turned any hash consisting only of decimal digits (such as the one of a flat image) into an integer or a lossy float; 237 hashes in the reference library were affected. The column is rebuilt as text on the next start (under 2 s); damaged values are cleared, and **Database Maintenance → Recompute Image Hashes** (default mode) refills them along with any older 64-bit hashes.

- **New: _Compact Database_ in Database Maintenance.** SQLite reuses the space left by deleted models, images and embeddings but never shrinks the file on its own. This rewrites it compactly (`VACUUM`) and then empties the write-ahead log, which `VACUUM` otherwise leaves as large as the database. The confirmation shows the database size and how much of it is free, the log reports the before and after sizes, and the progress bar shows a busy animation because `VACUUM` reports no progress. On a copy of the 1 GB reference library it took 8.8 s. `VACUUM`'s temporary copy of the database goes to a temp file instead of RAM. A concurrent write, such as a crawl, makes it fail with "database is locked" without changing anything.

- **Crawling moved archives is much faster.** On a 339-move crawl the end-of-crawl reconciliation took 6.5 minutes, about 1.15 s per move, after the same archives had already been extracted as new. Two causes, both fixed:
  - **Moves are now matched before extraction.** A new archive whose content hash matches exactly one missing record is relocated while the crawler compares archives with the database. It counts as unchanged, keeps its images, and is never decompressed, thumbnailed or embedded. Only moves that need the filename + size fallback are still reconciled after the crawl. The new folder's `METADATA.7z` is refreshed so it includes the moved record.
  - **Thumbnails are deleted in one transaction.** Every thumbnail-store write ends with a disk flush, measured at about 160 ms on the data drive, and images were deleted one transaction each: 3 s for a 20-image model against a few milliseconds batched. This applied to move reconciliation, removing deleted archives, re-crawling changed archives, _Delete Model_ (which ran on the GUI thread and froze the window), _Delete File_, _Regenerate Thumbnails_, _Prune Images_, _Update Crawled Folders_ and _Merge Moved_. Thumbnails of removed records are now deleted after the database commit, so a failed transaction no longer leaves images without thumbnails.
- **Fixed: moved models dropped out of folder views.** Move reconciliation stored the model's folder with backslashes (`F:\STL\…`), while the crawler stores forward slashes (`F:/STL/…`), so moved models formed separate branches in the filter pane's folder tree and were missed by folder lookups. The 238 affected records in the reference library are repaired on the next start.
- **Fixed: _Merge Moved_ left records flagged missing.** It updated the path but not the missing flag or the folder.
- Internally, the move logic that was copied in the crawler, _Update Crawled Folders_ and _Merge Moved_ now lives in one place, `app/services/moves.py`.

- **_Find by Image_: click a result to see its full thumbnail and model details.** A new _Selected Match_ panel shows the stored thumbnail at full size (scaled down to fit), with the model's title, creator, sculptor, collection and subcollection, category, release, release date, tags, image count, archive size and path, and whether the archive is missing. Empty fields are hidden. **Go to Model** shows the model in the main table and brings the main window to the foreground, restoring it if minimized; double-clicking a result does the same. The dialog stays open behind it and has its own taskbar button. On Windows a dialog owned by the main window always stays above it, so _Find by Image_ is no longer owned at window level. Clicking a result previously jumped straight to the main table.
- **_Find by Image_ shows at most the 1024 closest images,** for both the perceptual hash and the AI embedding, with one result per model. When more images match, the status line says so and suggests tightening the threshold. At loose thresholds the dialog used to build a grid of tens of thousands of thumbnails (27,702 models at similarity 0.5 on a 334k-image library). With the cap, an AI embedding search is always a single 1024-nearest query.

- **AI image embeddings now use sqlite-vec: _Find by Image_ is about 5x faster.** The CLIP vectors moved from a BLOB column on `images` into a sqlite-vec `vec0` table, `image_vec`, and the search runs as a nearest-neighbour query inside SQLite instead of streaming every vector into NumPy. On a 334k-embedding library a search at the default 0.85 similarity went from about 1.0 s to 0.2 s, and the database shrank from 1.7 GB to 0.96 GB.
  - **One-time move on first start.** Existing embeddings are copied into `image_vec`, the old `embedding` / `embedding_model` columns are dropped and the file is compacted. On the 334k library this took about 50 s, shown on the splash screen. Back up the database first if you may need to open it with an older version.
  - **Whole-table reads.** _Find Duplicate Archives → Images (AI embedding)_ loads its vectors in 0.9 s, as before. It reads sqlite-vec's chunk tables directly, which is 4.7x faster than reading the table row by row. That layout is internal to sqlite-vec, so the fast read is used only for checked versions (0.1.6–0.1.9) and only when the rows it decodes match the table's row count. Otherwise it falls back to the slower row-by-row read, and a test fails if an upgrade changes the layout.
  - **New requirement:** `sqlite-vec` (in `requirements.txt`, bundled in the executable). It needs a Python whose `sqlite3` module can load extensions. If it cannot be loaded, the embedding features are disabled and existing embeddings are left untouched, while everything else works as before.
  - Removed the **Configuration → Search batch** setting, which only tuned the old NumPy scan.
  - The SQLite memory-map window grew from 256 MB to 2 GB, because the nearest-neighbour search reads every vector and ran 2.8x slower with the smaller window.
  - Deleting an image or model removes its embedding through a per-connection trigger. **Compute Image Embeddings** also removes any embeddings left behind by images deleted outside the app.

- **The three image toolbar buttons now have distinct icons.** *Image Browsing* reused the *Image Grid* icon, and in the colour sets *Image Grid* and *Images* looked nearly identical. Each now has its own icon in every icon set: a grid of tiles, a photo stack or camera, and a single picture.

- **New: _Toolbar buttons_ option** in **Configuration → Appearance → Icons**: *Icon and text* (default) or *Icon only*, for the main toolbar. With icons only, each button's name shows as a tooltip. The change applies as soon as you press OK.

- **The _Models with presupported stl_ warning now only marks archives that really contain presupported meshes.** Its name patterns (`[_ -]presupported`, `sup_*.stl`) were applied to every archive member regardless of type, so a preview image called `Dragon - Presupported.jpg`, a `readme_presupported.txt`, or even a *directory* entry such as `Biker Mice from Mars Presupported lys` (archives list their folders as members) flagged an archive holding no presupported mesh at all. The rule now requires an `.stl`, which qualifies in either of two ways:
  - its own filename is marked (`body_presupported.stl`, `sup_arm.stl`), or
  - it sits under a folder that marks its contents (`Presupported/`, `PS/`, `Supported STL/`, `Pre-Supported/`, `Presupports/`).

  Folder names match on whole words, so `PSD Sources/` and `Props/` are not mistaken for `PS/`. An “unsupported” marker always wins, wherever it appears — in any folder above the file or in the mesh's own filename. That covers the common raw-mesh folders (`No_Supported/`, `No Supports/`, `Unsupported/`, `Non-Supported/`, `Not Supported/`, `Without Supports/`, `No_PS/` and merged spellings), and crucially the layout where raw meshes are nested *inside* the supported tree — `supports/Unsupported/120MM_Unsup_Emerald.stl` and its `NSFW_supports/NSFW_Unsupported/` twin — which the outermost-marker-wins reading got wrong. The test is per-file: a clean sibling such as `supports/120MM_Emerald.stl` is still flagged. Only a whole word counts, so `Dino Supported/` and `Casino PS/` still do. Non-`.stl` files in a presupport folder — slicer files, renders, readmes — do not qualify, and the warning details window now names the mesh that matched rather than its folder.
